# Aularia — contexto del proyecto (léeme al empezar)

## Qué es esto

Este repo era "Ivan Orgánico" (antes `teachable-clone`): una app Next.js + Supabase de un solo vendedor, un solo curso hardcodeado (`MAIN_COURSE_ID`), un admin global (`profiles.is_admin`), pagos con claves de Stripe/Whop globales.

Se está transformando en **Aularia**: una plataforma SaaS multi-tenant que se vende a varios clientes (creadores de cursos), cada uno con su propio portal, sus propios cursos, su propia gestión de alumnos, y sus propios cobros. El trabajo está organizado en **10 fases** (documento completo, con el detalle exacto de cada fase, en `/Users/jorgecamara/.claude/plans/luminous-hugging-snowflake.md` — ese archivo es la especificación granular; este SKILL es el resumen de orientación rápida).

**Antes de tocar código en cualquier fase pendiente**, lee también `docs/database.md` (fuente de verdad del esquema — este proyecto no tiene Prisma ni migraciones locales, todo SQL se aplica a mano en el dashboard de Supabase) y el archivo de plan de arriba para el detalle exacto de esa fase.

## Decisiones de arquitectura ya tomadas (no reabrir estas discusiones)

- **Portal por cliente**: originalmente se decidió por subdominio (`cliente1.aularia.app`); tras decidir (2026-08-07) quedarse en `*.vercel.app` sin dominio propio, se implementó además el enrutamiento por RUTA `/o/<slug>` (completo, no solo el mecanismo base — ver Fase 6 y la sección de dominio en `docs/database.md`). Los dos mecanismos conviven; hoy en producción manda la ruta, el subdominio real solo funciona en local (`*.localhost`).
- **Pagos de clientes**: Stripe **Connect** (cuentas **Express** + Account Links) para que el dinero les llegue directo sin que la plataforma vea su clave secreta. Whop no tiene Connect equivalente — el cliente pega su propia API key, cifrada en reposo.
- **Index principal** (`aularia.app`, sin subdominio): landing/registro de nuevos clientes-admin (metes nombre de empresa → crea una organización). No debe haber ahí un registro de alumno fácil de encontrar.
- **Subdominio de cada cliente**: SÍ tiene login/registro de alumno visible. Registrarse ahí mete al usuario en el roster de esa organización aunque no haya pagado nada. Un alumno puede pertenecer a varias organizaciones.
- **Roles**: `super_admin` (dueño de la plataforma, columna `profiles.is_super_admin`), `admin`/`owner` de una organización (tabla `organization_admins`, puede haber varios por empresa), `alumno` (tabla `organization_students`). No es un enum por usuario — alguien puede ser admin de una organización y alumno de otra.
- **Cursos por organización**: si tiene 1 solo curso publicado, se oculta el listado y se va directo a la ficha; si tiene varios, se muestra un listado (todavía no implementado, es Fase 4).
- **Nombre nuevo**: Aularia (sustituye a "teachable-clone"/"Ivan Orgánico" como marca de plataforma — el rebranding real de archivos es la Fase 8; "Ivan Orgánico" sigue siendo el nombre del PRIMER CLIENTE real, no se borra, solo deja de ser el nombre de la plataforma).

## Qué se construyó en cada fase hecha (para no re-descubrirlo)

### Fase 1 — Fundación multi-tenant
- Tablas nuevas: `organizations` (branding público), `organization_billing` (suscripción de plataforma, separada por seguridad), `organization_integrations` (claves Stripe/Whop del cliente, la más sensible), `organization_admins`, `organization_students`, `invitations`. `courses.organization_id` y `purchases.organization_id` (ambas NOT NULL). `profiles.is_super_admin` (nueva; `profiles.is_admin` queda **deprecada** pero viva de momento).
- Funciones `security definer`: `is_super_admin()`, `is_org_admin(org_id)`, `is_org_owner(org_id)`, `is_org_student(org_id)` — las usan tanto las policies RLS como el código de app (por RPC), para no duplicar lógica.
- `src/lib/auth/requireOrgAdmin.ts` (sustituye a `requireAdmin.ts`, borrado): `requireOrgAdmin(supabase, {courseId|sectionId|lessonId|organizationId})`, `requireSuperAdmin`, `requireAnyOrgAdmin` + `isAnyOrgAdmin`.
- `src/lib/organizations/getCurrentOrgMembership.ts`: helper compartido que resuelve `{organizationId, role}` del admin logueado (usado en `admin/layout.tsx` y `admin/usuarios/`).
- `src/proxy.ts`: resuelve el slug del subdominio y lo mete en el header `x-org-slug` (todavía sin consumidor — lo usará la Fase 4). Se borró un `proxy.ts` duplicado y obsoleto que había en la raíz del repo.
- Esquema completo documentado en `docs/database.md` — léelo ahí, no lo dupliques aquí.
- Segunda organización de prueba creada para verificar aislamiento entre clientes: slug `cliente-prueba`, admin `admin@cliente-prueba.test`. Se puede recrear/resetear la contraseña con `node --env-file=.env.local scripts/seed-second-test-org.mjs` (idempotente, imprime credenciales nuevas cada vez que se corre).

### Fase 2 — Verificación de email y recuperación de contraseña
- `registerAction` maneja el caso sin sesión tras `signUp()` (correo sin confirmar) mostrando "revisa tu correo" en vez de asumir sesión inmediata.
- `/forgot-password` y `/reset-password` nuevas. **Importante**: el proyecto NO tiene SMTP propio configurado en Supabase, así que las plantillas de email están bloqueadas (no editables) y usan el flujo clásico `{{ .ConfirmationURL }}` — la sesión llega en el fragmento `#` de la URL, no en query params. Por eso `ResetPasswordForm.tsx` detecta la sesión en el cliente (crea el browser client, `getSession()` espera a que se procese el fragmento) en vez de depender de una ruta servidor tipo `/auth/confirm` (esa ruta se construyó y se **borró** al descubrir que no se usaría con la plantilla bloqueada — si el usuario configura SMTP propio con Resend y cambia a la plantilla moderna con `token_hash`, habría que reconstruirla).
- Falta activar **"Confirm email"** en el dashboard de Supabase (Authentication → Providers → Email) para que la verificación entre en vigor de verdad — el código ya soporta ambos estados.
- **Sin probar de extremo a extremo con un correo real** (no hay acceso a bandeja de entrada desde aquí) — el usuario dijo que lo probaría él mismo "en la fase de bugs".

### Fase 3 — Invitar/echar alumnos, invitar co-admins
- `/admin/usuarios` reescrita: ahora escapa por organización (antes listaba TODOS los profiles del sistema). Tres secciones: Alumnos (Invitar/Echar/Reactivar), Administradores de la empresa (Invitar admin — solo visible para `role='owner'`, restricción a nivel de app, no de RLS — /Quitar), Invitaciones pendientes (Revocar).
- `src/lib/invitations/token.ts`: token aleatorio de 32 bytes, solo se guarda su hash SHA-256 en `invitations.token_hash`.
- `src/lib/resend/sendInvitationEmail.ts`: email de invitación vía Resend.
- `/invitaciones/[token]`: resuelve 4 casos (correo sin cuenta → crear contraseña; correo con cuenta y sesión coincidente → confirmar; sesión de otra cuenta → error; cuenta existente sin sesión → link a `/login?next=/invitaciones/[token]`).
- `loginAction`/`LoginForm` ahora soportan un `next` (validado contra open-redirect) para casos como el de arriba.
- `aprender/page.tsx` distingue "nunca compró" de "le echaron" (antes solo miraba `purchases`, dejando una experiencia confusa para alguien expulsado que aún tenía la fila de compra).
- Verificado en navegador con Playwright contra la organización `cliente-prueba`: invitar → aceptar creando cuenta → aparece en el listado → echar → cambia de estado. Sin errores de consola.

### Fase 4 — Branding dinámico y listado de cursos condicional
- `src/lib/organizations/getCurrentOrganization.ts` (nuevo, memoizado con `cache()` de React): resuelve la organización a partir del header `x-org-slug` (subdominio). **Fallback si no hay subdominio**: usa `DEFAULT_ORG_SLUG` (env var, `ivanorganico` en `.env.local` — hay que añadirla también en las env vars de Vercel en producción); si no está definida, cae a "solo si existe EXACTAMENTE una organización en toda la plataforma" (red de seguridad para un clon local nuevo). Se cambió de "solo si hay una organización" a la env var explícita porque ese fallback se rompió en cuanto se creó `cliente-prueba` (pasaron a haber 2).
- Consumido por `src/app/layout.tsx` (metadata dinámica vía `generateMetadata()`, `--accent` inline desde `organizations.primary_color`), `Header.tsx`/`Footer.tsx` (nombre, logo, "Creado con Aularia" solo si se resolvió por subdominio real), hero de `src/app/page.tsx` (`renderTagline()`, sustituye `{admin}` en `tagline_template`; si es `null` usa un genérico).
- `/cursos` reescrita: lista `courses` de esa organización con `status='published'` — 0 → vacío, 1 → redirect a la ficha, 2+ → listado. `MAIN_COURSE_ID` eliminado de `page.tsx`/`register/actions.ts`/`login/actions.ts` (ahora redirigen a `/cursos`). El único uso que queda es `api/webhooks/whop/route.ts`, dejado a propósito hasta la Fase 5 (un webhook no tiene subdominio del que resolver la organización).
- **Bug encontrado y arreglado (cross-tenant leak)**: `/admin/cursos` y `/admin/estadisticas` no filtraban por `organization_id` — como la policy de `courses` permite leer cualquier fila `published` de cualquier organización (a propósito, para el sitio público), cualquier admin veía en su panel los cursos de TODOS los clientes de la plataforma. Arreglado con `getCurrentOrgMembership()` + `.eq("organization_id", ...)`. Verificado con el admin de `cliente-prueba`: ya no ve nada de `ivanorganico`.
- **Hallazgo importante**: la organización real `ivanorganico` ya tenía 3 cursos publicados en la BD (2 invisibles hasta ahora por el hardcode de `MAIN_COURSE_ID`) — ahora los 3 aparecen en `/cursos`.
- Probado con `curl -H "Host: ..."` simulando subdominios (más rápido que Playwright para esto) y con un test de Playwright puntual para el fix del leak de admin — ambos limpiados al terminar. `npx tsc --noEmit` y `npx eslint` sin errores en todos los archivos tocados.

## Patrones y gotchas a tener en cuenta siempre

- **`node`/`npm`/`npx` no están en el PATH por defecto en este entorno** — hay que cargar nvm primero: `export NVM_DIR="$HOME/.nvm" && . "$NVM_DIR/nvm.sh" && nvm use v24.18.0` antes de cualquier comando de Node. Sin esto, `npm run dev`, `npx tsc`, etc. fallan con "command not found".
- Para levantar el server de dev y probarlo en navegador: usar Playwright directamente (`@playwright/test`, ya instalado junto con el navegador Chromium — `npx playwright install chromium` si hiciera falta de nuevo). No hay skill de "run" propia del proyecto; hay que escribir un script `.mjs` temporal DENTRO del repo (no en el scratchpad — la resolución de módulos ESM no encuentra `node_modules` fuera del proyecto) y borrarlo al terminar.
- Después de un `git pull`/merge que traiga cambios de `package.json` (como pasó con "tests y demas"), correr `npm install` — puede haber dependencias nuevas sin instalar (pasó con `@playwright/test`).
- Los mensajes tipo `[SYSTEM NOTIFICATION]` de diagnósticos del IDE tras un `Edit` a veces reflejan el estado justo ANTES de la edición (desfase de caché) — si el diagnóstico no tiene sentido con lo que se acaba de escribir, releer el archivo antes de asumir que hay un bug real.
- Los scripts de test de navegador con `waitForLoadState("networkidle")` + una captura inmediata pueden dar falsos negativos (la UI no había terminado de re-renderizar) — mejor usar esperas explícitas más largas o comprobar con logging de requests/respuestas antes de concluir que algo no funciona.
- Este proyecto no tiene Prisma ni migraciones — TODO cambio de esquema sigue el flujo de la skill `db-schema-change`: escribir el SQL, dárselo al usuario para pegar en el SQL Editor de Supabase, esperar confirmación, y solo entonces actualizar `docs/database.md`.
- **Antes de escribir cualquier insert nuevo, comprueba las columnas NOT NULL reales** con `GET {NEXT_PUBLIC_SUPABASE_URL}/rest/v1/` usando la service role key (swagger de PostgREST, `definitions.<tabla>.required`) — `docs/database.md` puede estar desactualizado o incompleto (pasó con `courses.description`/`learning_points` en la Fase 4). Ojo: `required` incluye columnas con DEFAULT de la base de datos (se pueden omitir igual), solo hace falta mandar explícitamente las que NO tienen `"default"` en las properties.
- **Cuidado con el límite de envío de emails de Supabase Auth** ("email rate limit exceeded") — se agota rápido en el plan gratuito si se prueban muchos `signUp()`/invitaciones/recuperaciones de contraseña seguidos en la misma sesión de pruebas (pasó en la Fase 6). Si un flujo de registro/checkout deja de avanzar sin más error visible, comprobar el texto exacto del `role="alert"` en la página (no asumir que es un bug del código) antes de rediseñar nada.
- Al escribir un `RegExp`/rango Unicode con acentos combinados (`̀-ͯ`) en el código de una tool call, el texto puede llegar corrompido/con caracteres literales en vez del escape — mejor evitarlo del todo y comparar por `codePointAt()` en un bucle (ver `src/lib/organizations/slug.ts`).
